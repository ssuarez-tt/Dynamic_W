期中项目：阅读进度追踪器
1. 应用程序目的与用户故事
这个应用是做什么的？
这是一个用于记录我正在阅读的书籍的清单。它记录了我每本书读到的确切页码，这样我再次开始阅读时，就不必再去记页码或到处找书签了。（这是一个为特定人群——同时阅读多本书的读者——设计的实用工具）。
用户故事
作为一个同时阅读多本书的读者，我希望直接在列表中记录每本书的当前页码，以便我能快速从上次停下的地方继续阅读，而无需回忆或寻找物理书签。
新字段：currentPage
•	类型：数字输入框（受控组件）。
•	默认值：新添加的书籍从第 0 页开始。
•	行为：它在列表中可见，支持内联编辑（而不仅仅是在创建时），通过 PATCH 请求保存到服务器，并且刷新页面后数据依然存在。

2. 开发者清单（写代码前的计划）
这是在编写任何代码之前写下的清单，列出了我认为添加新字段所需采取的每一个步骤（包含移动端计划与进度条构想）。
•	□ 表单与 UI：在图书录入表单中添加一个 currentPage 数字输入框，并在每条阅读清单行中也添加它，以便之后可以编辑。
•	□ 进度条构想：尝试利用 currentPage 字段结合预设的总页数（或简单的视觉比例），在书籍标题旁渲染一个可视化的阅读进度条（Progress Bar），让进度更直观。
•	□ 状态管理：在 React Context 的初始状态中添加 currentPage，并确保 reducer 处理更新操作，且能同步驱动进度条的更新。
•	□ API 集成：编写一个向 JSON Server 发送 PATCH 请求的函数（例如，PATCH /books/:id 伴随着 { "currentPage": value }）。
•	□ 端到端流程：确保捕获服务器返回的响应，并将其派发到 React Context 以更新 UI。
•	□ 错误处理：如果 PATCH 请求失败，显示有用的错误消息（例如“保存页码失败”），并将输入框和进度条恢复到之前的值。
•	□ 数据验证：阻止无效输入（例如负数、空字符串或纯文本）。
•	□ 移动端布局：使用 Tailwind 响应式类（如 flex-col md:flex-row）在小屏幕上将图书录入表单和阅读清单行垂直堆叠。
•	□ 移动端触控：确保移动端的内联 currentPage 输入框、进度条展示区域和“Save（保存）”按钮有足够的触控目标（至少 44x44px），防止误触。

3. 编写后的复盘清单与反思
这是在完成代码之后编写的修订版清单，对比了我实际必须做的事情和我遗漏的内容（包含移动端实际测试与进度条实现的反思）。
•	☑ 将 currentPage 添加到了表单和列表行中。
•	☑ 实现了 PATCH 请求和 React Context 的状态更新。
•	☑ 实现了错误处理以及失败时的状态回退。
•	☑ 完成了进度条的初步渲染，并测试了页码更新时进度条随之变化。
•	☑ 在窄屏视口（Chrome DevTools 的 iPhone 12 模式）下测试并修复了布局问题。
•	☑ 我遗漏了什么与实际遇到的坑（差距所在）：
o	完全忘了表单：我最初只把输入框加到了列表行中，忘了“添加图书”的表单也需要 currentPage 输入框来正确初始化它。
o	PUT 与 PATCH 的陷阱：我差点使用 PUT，它会替换整个记录，如果我只发送 currentPage，就会抹掉书名。后来改用了 PATCH。
o	空值处理：我没有测试当用户清空输入框（提交空字符串）而不是输入 0 时会发生什么。在添加严格的解析之前，它在 UI 中导致了 NaN 错误（使用了 parseInt(value) || 0）。
o	已有 db.json 的问题：数据库中的旧书没有 currentPage 字段，所以输入框显示 undefined，导致进度条代码直接崩溃。我不得不在渲染逻辑中添加一个回退值（book.currentPage || 0）。
o	进度条状态不同步：一开始，点击保存后页码更新了，但进度条没有重绘。后来发现是我在 Context 里直接修改了原对象的属性（mutate），改为返回新对象后才解决了重渲染问题。
o	移动端排版挤在一起：虽然计划了堆叠布局，但在移动端测试时发现，当书名过长时，输入框和保存按钮被挤出了屏幕。我加了 flex-wrap 并调整了移动端的边距（padding）才解决横向溢出问题。触控按钮也确实太小了，后来增加了高度。
